**Тон и стиль:** Прагматичный, прямой, без искусственной вежливости и поддакиваний. Строгое код-ревью, указание на архитектурные ошибки, плохой нейминг и нарушения SOLID.

## 2. Контекст проекта и наши пожелания
Мы разрабатываем веб-сервис для автоматической проверки выпускных квалификационных работ (ВКР) форматов `.docx`. 
**Цель:** Автоматизировать рутинный труд нормоконтролера, выявлять ошибки оформления (шрифты, отступы, поля, таблицы, списки литературы) и бороться с банальными обходами антиплагиата (подмена символов).
**Ограничения первой фазы (MVP):** Без применения ИИ/LLM (анализ смысла введения/выводов исключен). Только детерминированные алгоритмы, регулярные выражения, парсинг XML и PDF.

---

## 3. Технологический Стек

*   **Backend:** Python 3.10+, FastAPI (асинхронный API).
*   **База данных:** PostgreSQL + SQLAlchemy (хранение профилей настроек, задач, отчетов).
*   **Асинхронные задачи:** Celery + Redis (обработка документов вынесена в фон, чтобы не блокировать API).
*   **Парсинг документов:** 
    *   `python-docx`: для удобного обхода абзацев, стилей, секций.
    *   `lxml`: для прямого доступа к сырому XML Word (извлечение свойств списков, метаданных страниц, скрытых тегов).
    *   `PyMuPDF (fitz)`: для работы с PDF.
*   **Микросервис PDF-конвертации:** Gotenberg (изолированный Docker-контейнер для конвертации DOCX $\rightarrow$ PDF через headless LibreOffice).
*   **Frontend:** React 18 + Vite (SPA приложение).

---

## 4. Что берем из прошлого проекта (Анализ MVP)

**Оставляем:**
1. Разделение на Frontend (React) и Backend (FastAPI).
2. Pydantic-модели (схемы контрактов API `ReportResponse`, `Violation`).
3. Идею базового класса валидатора (но переписываем его на паттерн Strategy).

**Выкидываем:**
1. *Синхронный парсинг в эндпоинтах* $\rightarrow$ Переводим в Celery.
2. *Парсинг XML регулярными выражениями* $\rightarrow$ Переходим на строгий XPath через `lxml`.
3. *Огромные методы валидаторов (spaghetti code)* $\rightarrow$ Разделяем извлечение данных (DTO) и сами правила.
4. *Хардкод правил в коде* $\rightarrow$ Выносим настройки в БД и YAML-файлы (Configuration-Driven Design).

---

## 5. Скоуп задач: Нормоконтроль (39 пунктов вуза)

Набор правил жестко детерминирован и разбит на 5 доменов бизнес-логики:
1.  **Структура (`structure`):** Наличие Аннотации, Введения, Заключения, минимум 3 глав с выводами, сверка Содержания с текстом.
2.  **Типографика (`typography`):** Поля (30/15/20/20 мм), шрифт Times New Roman 14 пт, абзац 1.25 см, интервал 1.5, оформление заголовков (1 уровень — КАПС по центру, 2 уровень — влево с отступом).
3.  **Объекты (`objects`):** Таблицы (формат подписей, разрывы страниц, интервал 1.0), рисунки (подписи по центру), листинги кода (текстом, моноширинным шрифтом).
4.  **Библиография (`bibliography`):** $\ge 50$ источников, $\ge 5\%$ латиницы, $\le 50\%$ электронных URL (с датой обращения), кросс-чек цитат в квадратных скобках `[1]`.
5.  **Качество текста (`text_quality`):** Отсутствие многоуровневых списков, запрет англицизмов по словарю (бэкенд $\rightarrow$ серверная часть), защита от антиплагиата (смешивание латиницы и кириллицы в одном слове).
*Визуальные проверки (номера страниц, лимит 70-80 страниц)* выполняются через конвертацию в PDF.

---

## 6. Архитектура и Паттерны

Мы используем **Modular Monolith** с применением слоистой архитектуры (Clean Architecture).

1.  **Asynchronous Task Queue:** FastAPI только отдает `job_id`. Вся работа делается в фоне (Celery), клиент делает Long Polling.
2.  **Data Transfer Objects (DTO):** Слой `extractors` читает грязный DOCX/PDF и отдает чистые датаклассы (`DocumentDTO`, `ParagraphDTO`). Ядро не зависит от `python-docx`.
3.  **Strategy & Composite (Rule Engine):** Каждое правило ГОСТа — это отдельный класс, наследующий `BaseRule`. Движок правил собирает их в пайплайн.
4.  **Registry:** Правила регистрируются через декоратор `@register_rule`.
5.  **Graceful Degradation:** Если Gotenberg (PDF-конвертер) падает или виснет, система ловит таймаут, отключает зависящие от PDF правила и отдает частичный отчет, а не ошибку 500.
