Разложим архитектуру проекта по косточкам через призму фундаментальных инженерных принципов и паттернов проектирования.

Твои файлы (`handsoff.md`, `legacy_snippets.md`, `StructContext.md`) спроектированы грамотно: в них уже заложены основы **Clean Architecture**, но при непосредственном кодинге легко свалиться в антипаттерны. 

Ниже — детальный разбор: **какие принципы и паттерны здесь работают, почему они выбраны, где их границы и за какими ловушками нужно следить команде**.

### БЛОК 1. Базовые инженерные принципы (KISS, DRY, YAGNI)

#### 1. KISS (Keep It Simple, Stupid — «Не усложняй»)
Главная опасность этого проекта — превратить сервис проверки 100 работ в день в распределенный космолет с микросервисами, Kafka и нейросетями.

*   **Как реализован в архитектуре:**
    1.  **Модульный монолит вместо микросервисов:** Весь бэкенд живет в одной кодовой базе (`app/`), собирается в один образ и масштабируется просто запуском нескольких копий Celery-воркеров. Никакого gRPC, service discovery и распределенных транзакций.
    2.  **Отказ от ML/LLM на этапе MVP:** Проверка заголовков и цитат делается регулярными выражениями и синтаксическим анализом структуры (из `legacy_snippets.md`), а не отправкой в ChatGPT или локальную Llama. Это дает детерминированный результат (100% повторяемость), скорость (миллисекунды) и нулевую стоимость инференса.
    3.  **Gotenberg как готовый черный ящик:** Мы не пишем свой C++ биндинг к LibreOffice и не поднимаем сложные сокеты. Мы берем готовый контейнер и шлем туда один HTTP `POST`.
*   **Где нельзя нарушать:** Не пытайся внутри правил ГОСТа писать сложные грамматические парсеры. Если нужно проверить подпись к рисунку — используй `FIGURE_CAPTION_REGEX` из `legacy_snippets.md`. Это просто, быстро и надежно.

#### 2. DRY (Don't Repeat Yourself — «Не повторяйся»)
В старом коде (`coed.txt`) логика парсинга параграфов и извлечения шрифтов дублировалась внутри каждого валидатора.

*   **Как реализован в архитектуре:**
    1.  **Единый экстрактор (`DocxExtractor`):** Документ парсится **ровно один раз**. Экстрактор один раз вычисляет `indent_mm`, собирает `runs`, находит таблицы и упаковывает всё в `DocumentDTO`. Все 39 правил работают с готовым слепком данных, не переоткрывая zip-архив docx.
    2.  **Общие утилиты (`legacy_snippets.md`):** Функции вроде `normalize_whitespace` или `parse_bracket_content` вынесены в ядро и переиспользуются всеми правилами библиографии и заголовков.
    3.  **Configuration-Driven Presets:** Пороги (отступ 12.5 мм, поля 30/15/20/20) не захардкожены в 39 классах правил. Они вынесены в YAML-конфиг (`resources/rule_presets/`). Одно изменение в файле меняет поведение всей системы.
*   **Где нельзя нарушать:** Не дублируй логику поиска заголовков. Если `chapters_count.py` и `required_sections.py` ищут «ВВЕДЕНИЕ», они должны использовать общий фильтр или метод из `DocumentDTO`, а не писать свои регулярки заново.

#### 3. YAGNI (You Aren't Gonna Need It — «Тебе это не понадобится»)
*   **Как реализован в архитектуре:**
    1.  Мы выкинули проверку старых форматов `.doc` и `.rtf`.
    2.  Мы не делаем сложную ролевую модель с десятком уровней доступа (студент просто грузит файл по открытому API или токену, преподаватель смотрит дашборд).
    3.  Мы не пишем сложный собственный файловый сервер: временные файлы живут в `/tmp/` через `TempFileManager` и сразу удаляются.

### БЛОК 2. Принципы SOLID (Фундамент Clean Architecture)

Архитектура в `StructContext.md` строго подчинена принципам Роберта Мартина:

| Принцип SOLID | Где и как реализован в проекте | Чем грозит нарушение |
| :--- | :--- | :--- |
| **S (Single Responsibility)** | Каждый класс решает ровно одну задачу:<br>• `DocxExtractor` — только читает XML и строит DTO (он не знает правил ГОСТа).<br>• `ParagraphIndentRule` — только считает дельту отступа (он не знает, откуда взялся параграф).<br>• `jobs.py` (роутер) — только принимает HTTP и отдает JSON. | Если засунуть проверку отступов прямо в экстрактор, при изменении ГОСТа придется переписывать парсер Word. |
| **O (Open/Closed)** | **Движок правил (`RuleEngine`) закрыт для модификации, но открыт для расширения.**<br>Чтобы добавить 40-е правило кафедры, мы не трогаем код `engine.py`. Мы просто создаем файл в `rules/` и вешаем декоратор `@register_rule("RULE_40")`. Движок подхватит его на лету. | Без этого `engine.py` превратился бы в простыню из 2000 строк с бесконечными `if rule_name == '...'`. |
| **L (Liskov Substitution)** | Все правила наследуют абстрактный класс `BaseRule` (`app/rule_engine/base.py`) и реализуют метод:<br>`check(doc: DocumentDTO, params: dict) -> list[ViolationDTO]`.<br>Для движка правил абсолютно неважно, какое именно правило он выполняет: проверка полей или англицизмов. Все они взаимозаменяемы. | Если одно правило вдруг вернет строку вместо списка DTO или потребует другие аргументы, конвейер упадет в рантайме. |
| **I (Interface Segregation)** | Разделение DTO и схем API:<br>• `ParagraphDTO` содержит только распарсенные данные документа.<br>• `ViolationDTO` содержит только данные ошибки.<br>• `ReportResponse` в `schemas/report.py` отдает наружу только то, что нужно фронтенду. | Клиент API не должен зависеть от внутренних технических полей парсера. |
| **D (Dependency Inversion)** | **Ядро не зависит от библиотек парсинга.**<br>Модули правил в `rule_engine/rules/` зависят от абстрактных структур `DocumentDTO`, а не от объектов `docx.text.paragraph.Paragraph`. Если завтра мы заменим `python-docx` на другую библиотеку, ни одно правило проверки не сломается. | Прямой импорт `from docx import Document` внутрь правил проверки намертво свяжет бизнес-логику с конкретной библиотекой. |

### БЛОК 3. Паттерны проектирования (GoF и архитектурные)

В твоем проекте задействовано 7 ключевых паттернов:

#### 1. Strategy (Стратегия) — Поведенческий паттерн
*   **Где:** Вся папка `app/rule_engine/rules/`.
*   **Суть:** Каждое правило ГОСТа — это отдельная стратегия валидации (`MarginsRule`, `TablesRule`, `HomoglyphsRule`), реализующая общий интерфейс `BaseRule`.
*   **Зачем:** Позволяет изолированно тестировать каждое правило модульными тестами (unit-тестами) без поднятия базы данных и веб-сервера.

#### 2. Plugin / Registry (Реестр) — Архитектурный паттерн
*   **Где:** `app/rule_engine/registry.py`.
*   **Суть:** Словарь `RULE_REGISTRY = {}` и декоратор `@register_rule(id)`. При старте приложения все классы правил автоматически регистрируют себя в словаре. Фабрика берет имя правила из YAML-конфига и инстанцирует нужный класс по ключу.

#### 3. Data Transfer Object (DTO) — Корпоративный паттерн
*   **Где:** `app/domain/dto/`.
*   **Суть:** Объекты `DocumentDTO`, `ParagraphDTO`, `LocationDTO`.
*   **Зачем:** Очистка данных. Документ Word внутри полон мусора: закладки, ревизии, RSID-метки авторов, секции слияния. Экстрактор вычищает этот шум и передает правилам чистый объект с миллиметрами, строками и булевыми флагами.

#### 4. Adapter (Адаптер) & Facade (Фасад) — Структурные паттерны
*   **Где:** `app/adapters/extractors/` и `app/adapters/converters/gotenberg.py`.
*   **Адаптер:** `DocxExtractor` адаптирует проприетарную XML-модель Microsoft OpenXML к нашей доменной модели `DocumentDTO`.
*   **Фасад:** `GotenbergClient` скрывает за одним методом `convert_to_pdf()` весь кошмар сетевого взаимодействия: создание multipart-форм, отправку байтов, сетевые сокеты и обработку HTTP-кодов ошибок.

#### 5. Resource Acquisition Is Initialization (RAII) / Context Manager
*   **Где:** `app/adapters/storage/local.py` (`TempFileManager`).
*   **Суть:** Использование конструкции `async with TempFileManager(file) as path:`.
*   **Зачем:** Гарантия освобождения ресурсов. Файл на диске будет удален в блоке `finally` даже при падении воркера, делении на ноль или аварийном завершении задачи. Защита от утечки дискового пространства (Disk Exhaustion).

#### 6. Producer-Consumer (Поставщик-Потребитель) через очередь задач
*   **Где:** Связка `FastAPI` $\rightarrow$ `Redis` $\rightarrow$ `Celery Worker`.
*   **Суть:** Веб-сервер не ждет окончания работы. Он кладет задачу в Redis (Producer) и забывает о ней. Воркер (Consumer) забирает её по мере освобождения ресурсов CPU. Это спасает систему от падения при одновременной загрузке 20 дипломов.

#### 7. Graceful Degradation (Плавная деградация)
*   **Где:** `app/services/validation_pipeline.py`.
*   **Суть:** Если сервис Gotenberg перегружен или упал, конвейер перехватывает ошибку, логирует её, ставит флаг `pdf_available = False`, выполняет 35 проверок по структуре docx, а по 4 проверкам PDF выдает пользователю `Severity.WARNING` («Визуальная проверка нумерации временно недоступна»). Система **не падает с ошибкой 500**.

### БЛОК 4. Архитектурные ловушки (Чего категорически нельзя делать команде)

Когда вы с командой начнете наполнять кодом папки из `StructContext.md`, следи за тремя вещами:

1.  **Утечка библиотек наружу (Leaky Abstractions):**
    *   *Ошибка:* Внутри файла `app/rule_engine/rules/typography/margins.py` написать `import docx` или использовать `lxml`.
    *   *Норма:* Правило должно видеть **только** `DocumentDTO`. Вся работа с Word должна остаться в `app/adapters/extractors/`.
2.  **Антипаттерн God Rule (Правило-бог):**
    *   *Ошибка:* Сделать класс `FormatRule`, который внутри одного метода проверяет и поля, и шрифты, и отступы, и списки на 500 строк кода.
    *   *Норма:* Одно правило — один атомарный пункт регламента (`MarginsRule`, `ParagraphIndentRule`, `FontFamilyRule`).
3.  **Смешивание DTO и схем базы данных (Anemic Domain vs ORM):**
    *   *Ошибка:* Использовать SQLAlchemy-модель `Job` или `Report` внутри движка правил.
    *   *Норма:* Движок правил ничего не знает про БД. Он принимает DTO и возвращает DTO. Сохранением отчета в базу занимается только сервисный слой `validation_pipeline.py`.

За гибкую настройку правил из интерфейса (включение, отключение, смена порогов без программистов) в нашей архитектуре отвечает концепция **Configuration-Driven Design**. 

Это не один изолированный файл, а **сквозная цепочка из 5 компонентов**, проходящая через все слои системы: от кнопки в React до строчки в базе данных.

Давай я покажу на пальцах, **где конкретно это лежит в коде** и **как работает путь от клика мышки в UI до проверки документа**.

### Детальный разбор 5 ключевых элементов

#### 1. База данных: Хранилище настроек (`app/domain/models/profile.py`)
В модели `RuleProfile` есть специальная колонка:
```python
rules_config = mapped_column(JSONB, nullable=False)
```
В этой колонке PostgreSQL хранит состояние каждого правила. Выглядит это как обычный JSON-словарь:
```json
{
  "PARAGRAPH_INDENT": {
    "enabled": true,
    "expected_mm": 12.5,
    "tolerance_mm": 0.5
  },
  "FORBIDDEN_ANGLICISMS": {
    "enabled": false
  },
  "SOURCES_COUNT": {
    "enabled": true,
    "min_count": 50,
    "min_foreign_percent": 5
  }
}
```

#### 2. Контракты API: Схемы валидации (`app/api/schemas/profile.py`)
Здесь описано, что именно фронтенд имеет право прислать. Pydantic защищает систему от дурака (например, если методист случайно введет отступ `-10 мм` или `999 источников`):
*   `RuleParamSchema`: валидирует тип данных (число, строка, булево).
*   `ProfileUpdateSchema`: принимает новый словарь правил для сохранения.

#### 3. Эндпоинты управления: Ручки API (`app/api/routes/v1/profiles.py`)
Сюда стучится веб-интерфейс:
*   `GET /api/v1/profiles/{id}` — отдает текущие настройки профиля (чтобы фронтенд отрисовал тумблеры и инпуты).
*   `PUT /api/v1/profiles/{id}` — принимает измененный конфиг от преподавателя и перезаписывает `rules_config` в БД.
*   `POST /api/v1/profiles/{id}/reset` — сбрасывает настройки к дефолтным (накатывает чистый ГОСТ из файла `resources/rule_presets/gost_7_32_2017.yaml`).

#### 4. Движок правил: Фильтр активности (`app/rule_engine/engine.py`)
Вот сердце логики включения/отключения. Когда Celery-воркер начинает проверять диплом, он загружает `rules_config` выбранного профиля и делает простой отсев:

```python
# Упрощенная логика внутри RuleEngine:
for rule_id, rule_cls in RULE_REGISTRY.items():
    # 1. Достаем конфиг для этого правила из профиля
    config = profile_rules_config.get(rule_id, {})
    
    # 2. ЕСЛИ В ИНТЕРФЕЙСЕ ВЫКЛЮЧИЛИ ПРАВИЛО — ПРОПУСКАЕМ ЕГО!
    if not config.get("enabled", True):
        continue  # Правило вообще не запускается
        
    # 3. Если включено — передаем параметры из интерфейса в правило
    params = config.get("params", {})
    violations = rule_cls().check(document_dto, params)
    all_violations.extend(violations)
```

#### 5. Сами правила: Использование параметров (`app/rule_engine/rules/...`)
Внутри класса правила **нет захардкоженных чисел**. Правило берет их из словаря `params`, который прилетел из базы данных:
```python
class ParagraphIndentRule(BaseRule):
    rule_id = "PARAGRAPH_INDENT"

    def check(self, doc: DocumentDTO, params: dict) -> list[ViolationDTO]:
        # Берем число из интерфейса! Если не задано — 12.5 по умолчанию
        expected = params.get("expected_mm", 12.5)
        
        # Проверяем абзацы на соответствие числу `expected`...
```

### Сценарии из жизни: Как это работает на практике

#### Сценарий А. Нужно отключить правило (например, проверку англицизмов)
1. Преподаватель открывает панель управления на сайте.
2. Находит пункт *«Запрет англицизмов (бэкенд -> серверная часть)»*.
3. Переключает тумблер в положение `[ ВЫКЛ ]` и жмет «Сохранить».
4. Фронтенд шлет `PUT /api/v1/profiles/1` с `"FORBIDDEN_ANGLICISMS": {"enabled": false}`.
5. База обновляется. Следующий студент загружает работу со словом «бэкенд» — **ошибка больше не появляется**.

#### Сценарий Б. Кафедра изменила требования (например, нужно от 40 источников вместо 50)
1. Преподаватель в UI находит блок *«Список литературы»*.
2. В поле *«Минимальное количество источников»* стирает `50` и пишет `40`.
3. Жмет «Сохранить».
4. В базе в JSONB записывается `min_count: 40`.
5. Код движка правил теперь сравнивает длину списка с числом `40`. Программиста даже не будили.

#### Сценарий В. Появилось абсолютно НОВОЕ правило, которого раньше не было в коде
*(Например: кафедра придумала правило «Цвет заголовков должен быть строго синим»)*
*   Из интерфейса логику нового правила написать нельзя (ИИ мы сюда намеренно не пускаем).
*   **Действие разработчика:** Он создает один файл `app/rule_engine/rules/typography/heading_color.py`, описывает там проверку цвета и вешает декоратор `@register_rule("HEADING_COLOR")`.
*   При перезапуске бэкенда движок автоматически видит новое правило в реестре и добавляет его в список доступных настроек в интерфейсе методиста.
